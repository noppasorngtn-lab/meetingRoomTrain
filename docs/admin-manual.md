# คู่มือผู้ดูแลระบบ — ระบบจองห้องประชุม (mrr)

ฉบับแรก 2026-11-26 · ตอนนี้มีหัวข้อเดียว คือขั้นตอนนอกระบบที่ ADR-017 มอบให้ผู้ดูแลระบบทำเอง
ที่มา: [DQ-mrr-017](wiki/questions/DQ-mrr-017.md) (คำตอบลูกค้า · req SRC-040) · ADR-017 และ ADR-020 ใน `.aeon/design/changes.json` · คำตอบ Q-ADR017-1 และ Q-ADR017-2 ([req-design-request-adr017](qa/req-design-request-adr017-2026-11-25.md) · ผู้ใช้ตอบ 2026-11-25)

## 1. การปิดบังข้อมูลส่วนบุคคลของผู้ใช้ที่ไม่ active (ADR-017 / PDPA)

### 1.1 ข้อมูลที่อยู่ในขอบเขต

ข้อมูลส่วนบุคคลของผู้ใช้มีเพียงสองค่า คือ `User.email` และ `User.fullName` (ระดับ confidential) · ระบบ**ไม่มีงานตามเวลา**ที่ลบหรือปิดบังให้อัตโนมัติ ผู้ดูแลระบบต้องทำเองตามขั้นตอนด้านล่าง

### 1.2 จุดเริ่มนับ 1 ปี — ต้องจดนอกระบบ

- บัญชีกลายเป็น**ไม่ active** เมื่อไม่อยู่ในรายชื่อพนักงานที่นำเข้าจาก HR รอบล่าสุด
- เก็บข้อมูลส่วนบุคคลได้ **1 ปีนับจากวันนั้น**
- **ระบบไม่เก็บวันที่บัญชีเริ่มไม่ active** (ตาราง `users` มีแค่ `active` แบบ true/false · ADR-020 · `context.json` scope.outOfScope `inactive-since-date-tracking`)
- ⇒ ทุกครั้งที่นำเข้ารายชื่อจาก HR ผู้ดูแลระบบต้อง**จดรายชื่อบัญชีที่เพิ่งกลายเป็นไม่ active พร้อมวันที่**ไว้นอกระบบ (เช่น ทะเบียนของฝ่าย IT) เพื่อใช้นับครบ 1 ปี

### 1.3 เมื่อครบ 1 ปี — เขียนทับสองค่า

| ช่อง | ค่าใหม่ | หมายเหตุ |
|---|---|---|
| `full_name` | `ผู้ใช้ที่ถูกปิดบังชื่อ` | ข้อความนี้ตายตัว ใช้เหมือนกันทุกบัญชี |
| `email` | `masked-<uuid>@mrr.invalid` | `<uuid>` เป็น UUID ใหม่ต่อบัญชี (Q-ADR017-2) · โดเมน `.invalid` เป็นโดเมนที่สงวนไว้ให้ใช้ไม่ได้จริง จึงรับ Email ไม่ได้ · ค่าต้องไม่ซ้ำ — คอลัมน์ `users.email` เป็น UNIQUE ถ้าซ้ำฐานข้อมูลจะปฏิเสธเอง |
| `active` | คงเป็น `false` | ห้ามเปิดกลับเป็น `true` |

ตัวอย่างคำสั่ง (PostgreSQL · แทน `<user id>` และ UUID ทีละบัญชี):

```sql
update users
   set full_name = 'ผู้ใช้ที่ถูกปิดบังชื่อ',
       email     = 'masked-' || gen_random_uuid() || '@mrr.invalid'
 where id = '<user id>'
   and active = false;
```

`gen_random_uuid()` มีใน PostgreSQL 13 ขึ้นไป · ถ้าใช้ไม่ได้ ให้สร้าง UUID ข้างนอกแล้วใส่เป็นค่าตายตัว

### 1.4 สิ่งที่ห้ามทำ และสิ่งที่ยังอยู่หลังปิดบัง

- **ห้ามลบแถวผู้ใช้** — ร่องรอยการกระทำ การจอง และรายงานยังอ้างถึงผู้ใช้คนนี้อยู่ (BR-mrr-017@v3 ไม่เปลี่ยน)
- หลังปิดบัง หน้าจอที่แสดงชื่อ (ร่องรอย · การจอง · คำขอแก้ไข · รายงาน · ผู้อนุมัติประจำห้อง) จะแสดง "ผู้ใช้ที่ถูกปิดบังชื่อ" เอง เพราะทุกหน้าอ่านชื่อจากตาราง `users` ตอนแสดงผล
- ผู้ใช้ที่ถูกปิดบังไม่ได้รับ Email ใดๆ อีก เพราะระบบตัดบัญชีที่ไม่ active ออกจากผู้รับทุกกรณี (BR-mrr-007@v3)

### 1.5 สิ่งที่คู่มือนี้ยังไม่ครอบ

- ผู้ให้บริการส่ง Email จริงยังไม่ได้เลือก (DEC-005) · ยังไม่รู้ว่า SMTP ขององค์กรจะทำอย่างไรกับ address `.invalid`
- ขั้นตอนนำเข้ารายชื่อจาก HR และการตั้งค่าอื่นของระบบ ยังไม่ได้เขียน
