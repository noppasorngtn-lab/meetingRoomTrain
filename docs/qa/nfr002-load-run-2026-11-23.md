## อ่านผลอย่างไร

- ความหนาแน่น 3 เท่า (`dense`) ทำให้ max ของเคส 104 ขยับจาก 705 เป็น 740 ms — ยังห่างจาก 2 วินาทีราว 2.7 เท่า บน stack ทรัพยากร 1 CPU
- **ข้อจำกัด:**
  - รันโปรไฟล์ละ 1 รอบ ไม่ได้ทำซ้ำเพื่อดูความแปรปรวน
  - k6 กับระบบอยู่เครื่องเดียวกัน — ไม่มีเวลาเครือข่ายจริง และ k6 แย่ง CPU กับระบบ
  - วัดที่ API เท่านั้น · NFR-002 วัดที่หน้าจอ (ข้อ 2 ของใบคำขอ) จึงพิสูจน์ได้เพียงบางส่วนจนกว่า 104b จะรัน
  - ข้อมูลจำลอง ไม่ใช่ข้อมูลจริง (staging ยังไม่มีข้อมูล · PO 2026-11-23)
- ผลดิบของ k6 อยู่ใน scratchpad ของเซสชัน ไม่ได้เก็บเข้า repo — รันซ้ำได้ตาม `load/README.md`

## เคส 104b — วัดที่หน้าจอ (รอบเดียวกัน · รันหลัง 104/105)

**สคริปต์:** `load/nfr002-104b.k6.js` · image `grafana/k6:2.4.0-with-browser` · บริการ `web` เพิ่มใน `docker/docker-compose.staging.yml` (vite preview · port 4174)
**รูปแบบ:** ผู้ใช้ 200 คนในการยิงครั้งเดียว = 195 คนเรียก API + 5 คนเป็นหน้า Chromium จริงเปิดปฏิทินรายสัปดาห์ (UI-mrr-005) · k6 นัดทั้งสองกลุ่มจากเวลาเริ่มเทส จึงยิงพร้อมกัน · PO ยอมรับการสุ่มวัด 5 หน้าแทน 200 หน้า (2026-11-23)
**สัญญาณ "โหลดครบ" (ทาง ก):** ข้อความ "กำลังโหลดปฏิทิน…" (role=status) หายไป และมีช่องการจอง `ui-mrr-005-ent-007-start-at` หรือข้อความ empty · role=alert = ไม่ผ่าน · จับเวลาจาก `page.goto()` ถึงเฟรมแรกที่เงื่อนไขเป็นจริง

| โปรไฟล์ | API (195 คำขอ) max | ผิดพลาด API | หน้าจอ (5 หน้า) | สถานะที่เห็น | เกณฑ์ | ผล |
|---|---|---|---|---|---|---|
| `normal` | 1.25 s | 0% | 1.407–1.418 s (**max 1.41 s**) | data ทั้ง 5 | ทุกคำขอและทุกหน้า ≤ 2 วินาที | ✅ ผ่าน |
| `dense` | 1.19 s | 0% | 1.404–1.414 s (**max 1.41 s**) | data ทั้ง 5 | ทุกคำขอและทุกหน้า ≤ 2 วินาที | ✅ ผ่าน |

k6 exit 0 ทั้งสองรอบ · threshold ผ่านทุกข้อ

**อ่านผลอย่างไร:**
- เมื่อไม่มีโหลด หน้าเดียวกันแสดงข้อมูลครบใน 0.30 วินาที (ตรวจแยก 1 หน้า) · ใต้โหลด 200 คนเพิ่มเป็น ~1.41 วินาที — ระยะห่างจาก 2 วินาทีเหลือราว 0.6 วินาที แคบกว่าที่ 104 (API อย่างเดียว) บอกไว้มาก
- เวลาของหน้าทั้ง 5 ใกล้กันมาก เพราะยิงพร้อมกัน และคำขอปฏิทินของหน้าออกหลังโหลด JS จึงไปต่อท้ายคิวของการยิง 195 คำขอ
- API max ในรอบนี้ (1.19–1.25 s) สูงกว่ารอบ 104 (0.70–0.74 s) เพราะ Chromium 5 ตัวรันในเครื่องเดียวกันและแย่ง CPU
- คำขอของเบราว์เซอร์ที่ล้มเหลว 5 รายการ (หน้าละ 1) คือ `favicon.ico` 404 — ไม่กระทบผล
- **หน้าโหลดฟอนต์จาก Google Fonts ผ่านอินเทอร์เน็ต** (~0.1–0.2 s) · ถ้าเครื่องผู้ใช้ on-premise ออกอินเทอร์เน็ตไม่ได้หรือช้า เวลาบนหน้าจอจะเปลี่ยน — เป็นการพึ่งพาภายนอกที่ควรแจ้ง Dev / PO
- vite preview ตอบ 403 กับชื่อ host `web` (allowedHosts) · probe จึงเปิดหน้าผ่าน IP ของ container โดยไม่แก้ config ของแอป
- ข้อจำกัดเดิมยังอยู่: รันรอบเดียว · k6 กับระบบอยู่เครื่องเดียวกัน · ข้อมูลจำลอง · ไม่ใช่ staging จริง
