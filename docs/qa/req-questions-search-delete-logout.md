# คำถามถึง req: ตัวอย่าง (EX) ของ "ค้นหาห้องว่าง · ลบห้อง · ออกจากระบบ"

**ถึง:** req / BA / PO · **จาก:** QA (AI-assisted) · **สถานะ:** รอคำตอบ — ร่างคำถามเท่านั้น ยังไม่ได้เขียนอะไรลง spec

## ทำไมต้องถามตอนนี้

dev รายงาน DV6 ว่า 5 รายการไม่มีหน่วยงานรองรับ: `API-001`, `API-025`, `API-034`, `UI-mrr-003`, `UI-mrr-004`
ซึ่งตรงกับ 3 use case ที่ design **ไม่มีเกณฑ์รับ (AC) เลยสักข้อ**: UC-mrr-001, UC-mrr-015, UC-mrr-021 (dev ยกการ์ดไว้แล้ว: GAP-mrr-001 / 002 / 004)

design เขียน AC เองไม่ได้ เพราะ AC ต้องเป็นประโยคที่ req เขียนไว้ใน EX คัดลอกตรงตัว (เกต S16) — ต้นทางที่ขาดคือ **EX ของ req**

ตรวจโค้ดจริงแล้ว (2026-11-17) พบว่าทั้งสามอย่าง **ยังไม่ได้สร้าง** ไม่ใช่แค่ยังไม่ได้ผูกเอกสาร:

| ฟีเจอร์ | หลักฐานในโค้ด |
|---|---|
| ค้นหาห้องว่าง (UI-mrr-004 · API-001) | `apps/web/src/App.tsx` ไม่มี `UI-mrr-004` ใน `BUILT` จึงขึ้น `PendingScreen` · ไม่มี endpoint `/rooms/available` ใน `apps/api` |
| ลบห้อง (UC-mrr-015 · API-025) | `rooms.controller.ts` มีแค่ `@Patch` ไม่มี `@Delete` |
| ออกจากระบบ (UI-mrr-003 · API-034) | เมนูมีลิงก์ แต่ `UI-mrr-003` ขึ้น `PendingScreen` · `auth.controller.ts` ไม่มี logout |

> ผลที่ตามมา: "E2E ครอบ 105 จาก 105 EX" ไม่ได้แปลว่าระบบครบตามที่ลูกค้าคาด — EX ชุดนี้ไม่มีสามเรื่องนี้เลย

## คำถาม

คำถามละหนึ่งเรื่อง ตัวเลือกที่ติดป้าย **(เสนอ)** คือข้อเสนอของ QA ไม่ใช่คำตอบ — คนตัดสินคือ BA/PO

### Q1 · ค้นหาห้องว่าง (UC-mrr-001 · กฎที่เกี่ยว BR-mrr-001, BR-mrr-012)

design เขียน use case ไว้แล้ว: กรอกวันที่/เวลาเริ่ม–สิ้นสุด/จำนวนผู้เข้าร่วม/สิ่งอำนวยความสะดวก → แสดงห้องที่ความจุพอ ไม่ปิดปรับปรุง ไม่ถูกจองทับ (รวมที่รออนุมัติ)
ขาดคือ **ข้อความที่ผู้ใช้เห็นจริง** ที่ req ยืนยันได้:

1. ตัวอย่างปกติ — มีห้องตรงเงื่อนไข: ผู้ใช้เห็นอะไร (ชื่อห้อง/ความจุ/ปุ่มไปจอง?)
2. เวลาสิ้นสุดไม่หลังเวลาเริ่ม: ข้อความ error ที่ถูกต้องคือประโยคไหน
3. ไม่มีห้องตรงเงื่อนไข: ข้อความว่างพร้อมคำแนะนำคือประโยคไหน
4. ห้องที่มีการจอง "รออนุมัติ" ทับช่วงนั้น ถือว่าไม่ว่างจริงไหม (design เขียนว่า "รวมการจองที่รออนุมัติ" — ขอ req ยืนยันเป็นตัวอย่าง)

ปิดได้: GAP-mrr-001 · DV6 ของ API-001/UI-mrr-004

### Q2 · ลบห้อง (UC-mrr-015) — **ติดคำถามที่เปิดค้าง DQ-mrr-003**

use case ระบุเองว่า "ความหมายของ 'ลบ' รอคำตอบ DQ-mrr-003" (ลบจริง / ซ่อน-เก็บถาวร (archive)?) จึง**เขียน EX ไม่ได้จนกว่าจะตอบ DQ-mrr-003**
ตัวเลือกที่ QA เห็น:

| ตัวเลือก | ความหมาย | ผลต่อสิ่งที่มีอยู่ |
|---|---|---|
| **A. เก็บถาวร (archive) ไม่ลบแถว (เสนอ)** | ห้องไม่ปรากฏในการค้นหา/จอง แต่ข้อมูลเดิมและรายงานย้อนหลังอยู่ | ตรงกับสถานะ `ARCHIVED` ที่ระบบมีอยู่แล้วใน `meeting_rooms.status` และกับรายงานที่ไม่นับห้อง ARCHIVED · แก้ปัญหาห้องทดสอบลบไม่ได้ |
| B. ลบจริง | แถวหาย | ชนกับการจองเดิม/รายงานที่ append-only (BR-mrr-015) — ต้องมีกฎว่าห้องที่เคยมีการจองลบไม่ได้ |
| C. ลบไม่ได้ถ้ามีการจองในอนาคต | เงื่อนไขเพิ่มจาก A หรือ B | use case เขียนทางเลือก "แสดงรายการการจองที่ได้รับผลก่อนให้ยืนยัน" ไว้แล้ว |

แล้วขอ EX: (1) RA ลบห้องที่ไม่มีการจอง → ข้อความสำเร็จคืออะไร (2) ห้องมีการจองในอนาคต → ผู้ใช้เห็นอะไรก่อนยืนยัน (3) ผู้ใช้ที่ไม่ใช่ RA → ข้อความปฏิเสธ (ถ้าใช้ข้อความเดียวกับ BR-mrr-005 'เฉพาะผู้ดูแลห้องเท่านั้นที่จัดการข้อมูลห้องได้' ให้ยืนยัน)

ปิดได้: DQ-mrr-003 · GAP-mrr-002 · DV6 ของ API-025

### Q3 · ออกจากระบบ (UC-mrr-021)

design เขียนไว้: กดออก → ยกเลิก session → หน้า "ออกจากระบบแล้ว" พร้อมทางเข้าอีกครั้ง · ไม่มีกฎ (BR) ของการออกจากระบบ (BR-024–028 เป็นของการเข้า)
ขอ req: 
1. มีกฎหรือไม่ — หรือถือเป็นฟังก์ชันของแพลตฟอร์ม (ซึ่งให้ design เขียน AC เองได้ ไม่ต้องมี EX ตามประตู 116)
2. ถ้ามี EX: ข้อความหน้า "ออกจากระบบแล้ว" ที่ถูกต้อง · กรณียกเลิก session ไม่สำเร็จ ข้อความคืออะไร · ผู้ที่ไม่ได้เข้าสู่ระบบเปิดหน้านี้เห็นอะไร

ปิดได้: GAP-mrr-004 · DV6 ของ API-034/UI-mrr-003
