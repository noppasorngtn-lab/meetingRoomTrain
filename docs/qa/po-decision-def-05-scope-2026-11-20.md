# คำขอให้ PO ตัดสิน — DEF-05 และขอบเขตผลต่อเมลเหตุการณ์อื่น (2026-11-20)

ร่างโดย QA (AI) ให้ PO ตอบ · ผมไม่ตัดสินแทน PO · บริบท: [t4-def-05-2026-11-20.md](t4-def-05-2026-11-20.md) · โค้ดแก้แล้วใน `d1af479` แต่ยังไม่มีคำยืนยัน

## 1. สิ่งที่ตรวจได้ (ข้อเท็จจริงจากโค้ด `booking-notifier.ts`)

หลังแก้ `SmtpMailTransport.send()` ให้ล้มเมื่อผู้รับ**คนใดคนหนึ่ง**ถูก SMTP ปฏิเสธ พฤติกรรมของแต่ละเหตุการณ์เป็นดังนี้ (อ่านจากโค้ด ไม่ได้รันทุกเหตุการณ์)

| เหตุการณ์ | ผู้รับ | พฤติกรรมเปลี่ยนจากเดิมไหม | ถ้าผู้เข้าร่วมถูกปฏิเสธ |
|---|---|---|---|
| จองสำเร็จ (`bookingCreated`) | ผู้จองคนเดียว | **ไม่เปลี่ยน** (ผู้รับคนเดียว ถูกปฏิเสธ = ล้มอยู่แล้ว) | — |
| อนุมัติ (`bookingApproved`) | ผู้จองคนเดียว | ไม่เปลี่ยน | — |
| ยกเลิกอัตโนมัติ (`bookingAutoCancelled`) | ผู้จองคนเดียว | ไม่เปลี่ยน | — |
| **ยกเลิกการจอง** (`bookingCancelled`) | ผู้จอง + ผู้เข้าร่วม | **เปลี่ยน** | การยกเลิกล้ม ผู้ใช้เห็น "ส่ง Email แจ้งเตือนไม่สำเร็จ กรุณากดใหม่อีกครั้ง" |
| **ปฏิเสธการจอง** (`bookingRejected`) | ผู้จอง + ผู้เข้าร่วม | **เปลี่ยน** | การปฏิเสธล้ม RA เห็นข้อความเดียวกัน |
| **เปลี่ยนเวลา** (`bookingEdited` เฉพาะแก้เวลา) | ผู้จอง + ผู้เข้าร่วม | **เปลี่ยน** | การแก้ไขล้ม |
| **เตือนก่อนเริ่ม** (`reminderDue`) | ผู้จอง + ผู้เข้าร่วม | **เปลี่ยน (นี่คือ DEF-05)** | บันทึก `FAILED` ทั้งการจอง ไม่ส่งซ้ำ |

- `EmailDeliveryFailed` ถูกแปลงเป็น HTTP 503 ใน `booking.controller.ts` และ BR-mrr-019 ระบุว่าการกระทำที่ทำให้เกิดเมล "ล้มทันที ไม่บันทึก ให้ผู้ใช้กดใหม่" (EX-062–064 ของ BR-019 ทดสอบกรณี mail server ล่มทั้งตัวเท่านั้น)

### ผลทดลองจริง (2026-11-20 · stack จริงหลังแก้ `d1af479` · SMTP fixture ปฏิเสธเฉพาะ `e2e.u3@mrr.local` · การจองมีผู้เข้าร่วม U2, U3)

| การกระทำ | HTTP | ข้อความ | สถานะ/เวลาการจองหลังกระทำ |
|---|---|---|---|
| ผู้จองยกเลิก (`/cancel`) | **503** | ส่ง Email แจ้งเตือนไม่สำเร็จ กรุณากดใหม่อีกครั้ง | `CONFIRMED` คงเดิม |
| RA ยกเลิกแทนหลังประชุมเริ่ม (`/admin-cancel` · ตั้งนาฬิกาหลังเวลาเริ่ม) | **503** | เหมือนกัน | `CONFIRMED` คงเดิม |
| RA ปฏิเสธการจอง (`/reject` ห้องต้องอนุมัติ) | **503** | เหมือนกัน | `PENDING_APPROVAL` คงเดิม |
| ผู้จองเปลี่ยนเวลา (`PATCH`) | **503** | เหมือนกัน | เวลาเดิมคงอยู่ |
| ผู้จองแก้เฉพาะหัวข้อ (ไม่ส่งเมล · ตัวควบคุม) | 200 | บันทึกการแก้ไขสำเร็จ | แก้สำเร็จ ไม่มีเมลจึงไม่ถูกปฏิเสธ |

- ทุกกรณีที่ล้ม ฟิกซ์เจอร์ยืนยันว่าปฏิเสธ `e2e.u3@mrr.local` จริง (ล้มเพราะการปฏิเสธ ไม่ใช่เพราะต่อ SMTP ไม่ติด) และการกระทำถูกยกเลิกทั้งหมด ตรวจจากสถานะ/เวลาหลังกระทำผ่าน API — ไม่ได้ตรวจแถวใน DB และ audit trail
- ความหมาย: พฤติกรรมตอนนี้ = Q2(ก) (ล้มทั้งการกระทำ) เกิดจริงทั้ง 4 การกระทำ · ผู้เข้าร่วมที่เมลมีปัญหาคนเดียวทำให้ผู้จองยกเลิก/เปลี่ยนเวลาไม่ได้ และ RA ปฏิเสธไม่ได้ (ผู้จองยังแก้รายชื่อ/หัวข้อได้เพราะไม่ส่งเมล)
- ข้อจำกัด: ผู้เข้าร่วมถูกปฏิเสธ 1 คน (U3) · ไม่ได้ทดลองกรณีผู้**จอง**ถูกปฏิเสธ · ไม่ได้ทดลองอนุมัติ/จองสำเร็จ (ผู้รับคนเดียว) · เป็น probe ชั่วคราว (ลบแล้ว ไม่ใช่เคสถาวร) · ผลดิบเก็บนอก repo ที่ %TEMP% (`probe-out.json`, `probe-out2.json` อาจถูกล้าง) ·  การจอง E2E ที่ probe สร้างค้างใน DB dev ตามปกติของเคส E2E (หัวข้อ `E2E probe …`)
- ผลกระทบเชิงปฏิบัติที่ต้องชั่งน้ำหนัก: ผู้เข้าร่วมคนเดียวที่อีเมลมีปัญหา (กล่องเต็ม / ที่อยู่ผิด) ทำให้**ผู้จองยกเลิก/เปลี่ยนเวลาไม่ได้** และ RA ปฏิเสธการจองไม่ได้ จนกว่าจะแก้ที่อยู่หรือเอาผู้เข้าร่วมคนนั้นออก (ข้อนี้เป็นข้อสังเกตของ QA ไม่ใช่ข้อมูลจากการทดลอง)
