# ขอให้ลูกค้า / BA ตัดสิน: ปฏิทิน · รูปภาพห้อง · สิ่งอำนวยความสะดวก (GAP-mrr-011, 012, 016, 018)

**ผู้ตัดสิน:** ลูกค้า / BA / PO · **ผู้เตรียมเอกสาร:** QA (AI-assisted) · **สถานะ:** ตัดสินแล้ว 2026-11-17 โดย Noppasorn Y (011 A · 012 A · 016 B · 018 A) — ดูหัวข้อ "บันทึกการตัดสิน" ท้ายเอกสาร
**ที่มา:** การ์ดที่ dev ยกถึง design (`.aeon/dev/features.json`) ตอนสร้างหน้าจอจริงแล้วพบว่าดีไซน์ที่เซ็นไว้ไม่พอให้ใช้งาน
ทั้งสี่เรื่องเป็น **ขอบเขตผลิตภัณฑ์** (ผู้ใช้ทำอะไรได้) ไม่ใช่รายละเอียดทางเทคนิค — จึงต้องให้เจ้าของงานตอบ

ทุกข้อมี 3 ส่วน: *เป็นอยู่ตอนนี้* (ตรวจกับดีไซน์และโค้ดจริง 2026-11-17) · *ทางเลือก* · *สิ่งที่ต้องแก้ถ้าเลือก* ข้อที่ติดป้าย **(เสนอ)** คือข้อเสนอของ QA ไม่ใช่คำตอบ

## 1. ปฏิทินห้อง: เลื่อนวันไม่ได้ (GAP-mrr-011 · UI-mrr-005)

**เป็นอยู่ตอนนี้** ดีไซน์ให้ดูปฏิทินรายวัน/สัปดาห์/เดือน มีแค่ปุ่ม "เปลี่ยนมุมมอง" ไม่มีปุ่มก่อนหน้า/ถัดไปหรือเลือกวัน
โค้ดอ่านวันที่จาก `?date=` ใน URL เท่านั้น (ไม่ใส่ = วันนี้) ผู้ใช้จึงเปิดมุมมองสัปดาห์ได้ แต่ **เลื่อนไปสัปดาห์ถัดไปไม่ได้** ถ้าไม่แก้ URL เอง

| ทางเลือก | ผล |
|---|---|
| **A. เพิ่มปุ่ม ก่อนหน้า / ถัดไป / เลือกวัน (เสนอ)** | ใช้ปฏิทินดูล่วงหน้าได้จริง · ต้องเพิ่ม field/action ใน `screens.json` (UI-mrr-005) |
| B. คงเดิม ให้ผู้ใช้เข้าจากหน้าอื่นพร้อมวันที่ | ไม่แก้ดีไซน์ แต่ "รายสัปดาห์/รายเดือน" แทบไม่มีประโยชน์ |

**ต้องรู้เพื่อตอบ:** ปุ่มควรชื่ออะไร (เช่น "ก่อนหน้า" "ถัดไป" "วันนี้") และเลือกวันด้วยช่องวันที่หรือไม่

## 2. ปฏิทินห้อง: เลือกช่วงเวลาไปจองอย่างไร (GAP-mrr-012 · UI-mrr-005)

**เป็นอยู่ตอนนี้** ดีไซน์มี action "จองช่วงที่ว่าง" ที่ **"เปิดฟอร์มจองพร้อมช่วงเวลาที่เลือก"** แต่หน้าปฏิทินไม่มี field ให้เลือกช่วงเวลา และ API-003 ส่งเฉพาะช่วงที่ *ไม่ว่าง*
โค้ดส่งแค่ห้องกับวันที่ (`?room=&date=`) ไปหน้าจอง แล้วผู้ใช้กรอกเวลาในฟอร์มเอง — **ต่างจากถ้อยคำของดีไซน์** ("พร้อมช่วงเวลาที่เลือก" ไม่เกิดขึ้นจริง)

| ทางเลือก | ผล |
|---|---|
| **A. ยอมรับพฤติกรรมปัจจุบัน แก้ถ้อยคำ action เป็น "ไปหน้าจองห้อง" (เสนอ)** | ไม่เพิ่มงานสร้าง · แก้ข้อความใน `screens.json` ให้ตรงของจริง |
| B. กดช่องว่างในตารางเพื่อส่งเวลาเริ่ม–สิ้นสุดไปหน้าจอง | ใช้สะดวกที่สุด แต่ต้องให้ API ส่งช่วงที่ *ว่าง* (หรือคำนวณจากช่วงไม่ว่าง) และสร้างตารางที่กดได้ — งานใหม่ขนาดกลาง |
| C. เพิ่มช่องเวลาเริ่ม/สิ้นสุดบนหน้าปฏิทิน | ซ้ำกับฟอร์มจอง |

**ต้องรู้เพื่อตอบ:** ลูกค้าคาดหวังว่า "กดช่องว่างแล้วไปจองต่อ" หรือแค่ "ดูว่าช่วงไหนว่างแล้วไปจองเอง"

## 3. รูปภาพห้อง: เพิ่ม/เปลี่ยนรูปไม่ได้ (GAP-mrr-016 · UI-mrr-013)

**เป็นอยู่ตอนนี้** ฟอร์มห้องมีช่อง "รูปภาพ" (`ไฟล์ภาพ ไม่บังคับ` · ถ้าใหญ่เกินต้องแจ้งที่ช่อง) แต่ **ไม่มี API อัปโหลดไฟล์** — API-021/023 รับ `photos` เป็นรายการ id ของไฟล์
โค้ดจึงแสดงแค่จำนวนรูปและส่งรูปเดิมกลับทุกครั้งที่บันทึก: **ห้องใหม่ไม่มีรูปได้เท่านั้น เพิ่มหรือเปลี่ยนรูปไม่ได้เลย**

| ทางเลือก | ผล |
|---|---|
| **A. สร้างการอัปโหลดรูป (ถ้ารูปอยู่ในขอบเขตรอบนี้)** | ต้องเพิ่ม API ใหม่ใน `interfaces.json` + สิทธิ์ใน `rbac.json` + ที่เก็บไฟล์ + หน้าจอ · **ต้องกำหนด 3 ค่าก่อน** (ด้านล่าง) |
| B. ตัดรูปภาพออกจากรอบนี้ (ซ่อนช่อง/แสดงว่ายังไม่เปิดใช้) | ไม่มีงานสร้าง แต่ต้องแก้ดีไซน์ UI-mrr-013 ให้ตรง และแจ้งลูกค้าว่ายังไม่มี |

**ถ้าเลือก A ต้องให้ลูกค้ากำหนด** (QA ไม่ใส่ตัวเลขแทน): ขนาดไฟล์สูงสุดต่อรูป · ชนิดไฟล์ที่รับ · จำนวนรูปสูงสุดต่อห้อง
**ต้องรู้เพื่อตอบ:** รูปห้องอยู่ในขอบเขตที่ลูกค้าจะรับมอบรอบนี้หรือไม่ (ผู้ใช้ทั่วไปไม่เห็นรูปอยู่แล้วตามการตัดสิน GAP-mrr-013 — รูปใช้เฉพาะผู้ดูแลห้อง)

## 4. สิ่งอำนวยความสะดวก: ปิดใช้แล้วเปิดกลับไม่ได้ (GAP-mrr-018 · UI-mrr-014)

**เป็นอยู่ตอนนี้** หน้าจอให้ปิดใช้ ("ปิดแล้วไม่แสดงเป็นตัวเลือกใหม่ ข้อมูลเดิมคงไว้") แต่ API อ่านรายการมีแค่ `GET /facilities?active=true` (API-002)
สิ่งที่ปิดใช้แล้วจึง **หายจากหน้าเมื่อโหลดใหม่ และเปิดกลับไม่ได้** (หน้าไม่เห็นมันแล้ว)

| ทางเลือก | ผล |
|---|---|
| **A. ให้ผู้ดูแลห้องอ่านรายการทั้งหมดรวมที่ปิดใช้ (เสนอ)** | เปิดกลับได้ · ต้องเพิ่มความสามารถของ API (เช่น `GET /facilities` ไม่ระบุ `active`) + สิทธิ์เฉพาะผู้ดูแลห้องใน `rbac.json` — งานเล็ก |
| B. ยืนยันว่าปิดใช้แล้วถาวร เปิดกลับไม่ได้ | ไม่มีงานสร้าง · แก้ข้อความดีไซน์ให้บอกชัดว่าถาวร (เหมือนที่ตัดสินกับการลบห้อง = archive) |

**ต้องรู้เพื่อตอบ:** ผู้ดูแลห้องเคยปิดใช้ผิดแล้วต้องเปิดกลับหรือไม่ · (หมายเหตุ: ระบบ dev ตอนนี้ยังไม่มีรายการสิ่งอำนวยความสะดวกเลย จึงยังไม่เคยถูกทดสอบกับของจริง — ดู `test/README.md`)

## ผลต่อเอกสารที่ลงนามแล้ว (ถ้าเลือกทางที่แก้ดีไซน์)

ทุกทางเลือกที่ไม่ใช่ "คงเดิม" แตะ `screens.json` / `interfaces.json` / `rbac.json` ซึ่งลงนามแล้ว ขั้นตอนต่อข้อ:
ADR (ตามที่ตัดสิน) → ปลดลายเซ็นไฟล์ที่เกี่ยวด้วย ADR นั้น → แก้ผ่านคำสั่งของ design → `check.mjs` → **คนอ่านแล้วเซ็นใหม่** → `dev:plan` (หน่วยที่ถือ UI/API นั้น) → `dev:build` → เพิ่มเคส E2E
