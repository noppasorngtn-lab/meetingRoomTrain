## คำตอบ

### ข้อ 1 — ตอบโดย req (2026-11-23)

**ยึดค่าของ req: "ทุกคำขอ" ≤ 2 วินาที และ "200 คนกดพร้อมกันครั้งเดียว" · ไม่ต้องมีเคสต่อเนื่อง 30 นาที**

เจ้าของตอบเรื่องนี้ไว้แล้วเป็นตัวเลือกที่ชัดใน [oq-nfr-questions-2026-11-18.md](oq-nfr-questions-2026-11-18.md) (req บันทึกเป็น SRC-034):

| คำถาม | ตัวเลือกที่ให้เลือก | เจ้าของตอบ |
|---|---|---|
| 1b. เกณฑ์ 2 วินาที | (ก) ทุกคำขอ · (ข) p95 · (ค) ค่าเฉลี่ย | **(ก) ทุกคำขอ** |
| 1d. นับ "พร้อมกัน" | (ก) 200 session ทำงานต่อเนื่อง · (ข) 200 คนกดพร้อมกันครั้งเดียว | **(ข) ครั้งเดียว** |

- p95 กับต่อเนื่อง 30 นาทีไม่ใช่ทางเลือกที่ยังเปิดอยู่ เพราะเจ้าของเห็นทั้งสองแบบในใบคำถามและเลือกอีกแบบ
- ไม่ต้องมีทั้งสองเคส เพราะ req ไม่มีข้อกำหนดเรื่องความทนทานต่อเนื่อง · ถ้าทีมอยากทดสอบ 30 นาทีไว้เป็นข้อมูลเสริม ทำได้ แต่ต้องติดป้าย "นอกเกณฑ์ req" และผลของเคสนี้ห้ามทำให้ NFR-002 ผ่านหรือไม่ผ่าน · ถ้าจะให้เป็นเกณฑ์จริง ต้องกลับไปถามเจ้าของใหม่
- ค่าใน `nfr.json` (p95 · 30 นาที) ลงนามวันที่ 2026-10-19 ก่อนเจ้าของตอบ (2026-11-18) จึงเป็นค่าที่ design ร่างไว้ก่อนมีคำตอบ ไม่ได้มาจากธุรกิจ
- ผลต่อ QA: เคส TC-NFR-REQ001-104/105 (`load/nfr002.k6.js`) ที่เขียนตาม req ถูกต้องแล้ว ไม่ต้องแก้

**ที่ยังค้างจากข้อนี้:** design ต้องแก้ `nfr.json` ผ่าน `/design:change` หรือ `/design:nfr` แล้วให้คนลงนามใหม่ · เส้นทางส่งเรื่องให้ design (ออก CHG ฝั่ง req หรือให้ design เปิดรอบเอง) ยังรอตัดสินในข้อ 4 · ข้อ 2 ยังเปิดอยู่ เพราะเจ้าของตอบ 1a ว่า "ตารางแสดงข้อมูลครบ" ซึ่งเป็นภาษาของหน้าจอ ส่วนการวัดที่ API เป็นการตัดสินของ Dev ไม่ใช่ของเจ้าของ

### ข้อ 2 — ตอบโดย Dev (2026-11-23)

**ธุรกิจหมายถึงหน้าจอ · เคส 104 ที่วัดที่ API พิสูจน์ได้เพียงบางส่วน · ต้องเพิ่มการวัดในเบราว์เซอร์**

- เจ้าของตอบ 1a ว่า "ตารางห้องแสดงข้อมูลครบ" (SRC-034) และ `nfr.json` เขียนว่า "จนข้อมูลแสดงครบบนหน้าจอ" · ต้นน้ำทั้งสองฝั่งตรงกัน
- ที่ Dev เลือกวัดที่ API (`load/README.md`, [t1-nfr-2026-11-23.md](t1-nfr-2026-11-23.md)) เป็นความสะดวกในการวัด ไม่ใช่การตีความเกณฑ์ใหม่
- หน้า `CalendarPage` เรียกข้อมูลครั้งเดียว (`GET /rooms/:id/calendar?view=week`, `apps/web/src/features/calendar/CalendarPage.tsx:76`) · เวลาบนหน้าจอ = เวลา API + โหลดหน้า/JS + เรนเดอร์ · API ≤ 2 วินาทีจึงจำเป็นแต่ยังไม่พอ

Dev เสนอให้รันพร้อมกันสองชั้น:

| ชั้น | วิธี | พิสูจน์อะไร |
|---|---|---|
| 104a (มีแล้ว) | k6 ยิง 200 คำขอพร้อมกันครั้งเดียว · ทุกคำขอ ≤ 2 วินาทีที่ API | เซิร์ฟเวอร์รับ 200 คนไหว |
| 104b (ใหม่ · ยังไม่ได้เขียน) | ระหว่างที่ k6 ยิงอยู่ ให้เบราว์เซอร์จริงจำนวนหนึ่ง (Playwright เช่น 5 ตัว) เปิดหน้าปฏิทินรายสัปดาห์ แล้วจับเวลาจนช่องการจองหรือสถานะ "ว่าง" แสดงครบ · ทุกตัว ≤ 2 วินาที | ผู้ใช้เห็นตารางครบภายใน 2 วินาทีขณะระบบรับโหลดเต็ม |

**ที่ Dev ตัดสินเองไม่ได้:**
- **PO:** เกณฑ์คือ "ทุกคำขอ" ถ้าตีความตรงตัวที่ระดับหน้าจอ ต้องเปิดเบราว์เซอร์จริง 200 ตัว ซึ่งเครื่องเดียวทำไม่ไหว · 104b จึงวัดแค่ตัวอย่างบางส่วน แล้วอาศัย 104a รับประกันว่าทุกคำขอที่ API ผ่าน · ต้องให้ PO ยอมรับวิธีนี้ก่อนจึงจะนับว่าพิสูจน์ NFR-002 ได้
- **design:** ตารางยังไม่มี testid ที่บอกว่าข้อมูลมาครบแล้ว · testid เป็นของ design (gate 45) · ทางเลี่ยงคือรอ testid `ui-mrr-005-ent-007-*` หรือรอข้อความสถานะว่าง ซึ่งใช้ได้แต่เปราะกว่า

### ข้อ 3 — ตอบโดยผู้ใช้ในเซสชัน (2026-11-23 · ไม่ได้ระบุบทบาท)

### ข้อ 4 — ตอบโดย design (2026-11-23)
